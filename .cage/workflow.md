# 工作流约束

## 0. 任务受理评审（动手前必做）

用户下达任何任务后，**不立即执行**，先输出评审四要素：

1. **优点**：这个方案 / 做法好在哪。
2. **风险**：潜在风险与代价（正确性、性能、兼容、数据安全、工作量）。
3. **理念冲突**：方案若违背了本仓库约束或项目理念（红线、架构不变量、流程规范、目录规范），即使符合用户要求，也必须逐条说明**违背了哪条理念**（引用具体条款），不得回避。
4. **评分**：按下方标准打分（满分 100），并给出结论（建议执行 / 需注意 / 需确认 / 不建议）。

**评分标准（满分 100）**

| 维度 | 分值 | 扣分 |
|---|---|---|
| 合规 | 40 | 触碰红线每处扣 10–40；违背理念（如默认值未经评估、语义被改、目录放错）每处扣 10–30 |
| 风险 | 30 | 已知风险按程度扣 5–25 |
| 可验证 | 15 | 无明确验证手段（冒烟 / A/B / 日志断言）扣 5–15 |
| 性价比 | 15 | 收益与工作量不匹配扣 5–15 |

**结论档位**：≥85 建议执行；70–84 可执行但需注意风险点；60–69 部分违背理念，须用户确认后执行（附违背条目）；<60 不建议直接执行，先改方案。

评审输出后等用户确认再动手；用户明确说"直接做 / 不用评审"时跳过评审直接执行。

## 1. 修 bug 状态机（照做，不跳步）

```
新报 → 登记 → 取证 → 定位 → 根因成立 → 修复设计 → 方案归档(docs/scheme)
     → 实施 → 本地验证 → 冒烟前保存记忆 → 回归验证(冒烟) → 结果归档(docs/summary)
     → 提交 → 关闭 + 复盘
```

复现不是必经步骤：有日志就用日志取证；没有日志时根据用户描述从代码推断；推断不足以定论时，启动本地测试服自己跑一遍（见 §4）。

## 2. 登记（每单必填）

标题、版本（PRTS-`<MC>`-`<version>`-`<branch>`，以 jar 的 Implementation-Version 为准）、现象（何时 / 何操作 / 何表现）、影响（哪些玩法 / 模组受影响）、能否复现（是 / 否 + 步骤）、现场（`latest.log` / crash-report / `servercore status` / 配置）。

## 3. 取证（先别改任何东西）

`tail -n 300 logs/latest.log`、`ls -t crash-reports/ | head -3`、RCON `tps`、RCON `servercore status`、解包核对 MANIFEST 的 Implementation-Version。

## 4. 复现（可选，仅在取证不足时）

1. 优先用用户提供的日志（`latest.log` / crash-report / `servercore status` / 配置）+ 现象描述取证。
2. 无日志：根据用户描述对照代码静态走查（必要时字节码核实），推断出最可能的路径。
3. 推断仍不足以定论：启动本地测试服（`prts-test`）自己跑一遍——写复现协议：环境、配置、坐标、操作序列、预期 vs 实际。
4. 单变量矩阵：一次只改一个开关，每行记「复现 / 不复现」。
5. 合成负载替代真人：forceload 区块柱 + summon 实体 + 漏斗回路。
6. 复现失败也记录——说明还缺条件，继续找。

## 5. 定位（四层证据链）

| 层 | 手段 | 回答 |
|---|---|---|
| L1 日志 / 状态 | grep crash-report / latest.log / status | 发生了什么 |
| L2 静态 / 字节码 | 源码 + javap | 代码为什么这样走 |
| L3 运行时采样 | spark / JFR / thread dump | 调用链是否真的发生 |
| L4 受控复现 | 单变量测试服 | 因果，而非相关 |

对任何引擎 / 总线行为的断言，必须先到 L2（字节码）核实再下结论。计划基于的版本假设与实际不符时（如文档假设的 bus 版本与实装不符），按字节码修正并记录偏差。

## 6. 根因陈述模板

```
现象：...
触发条件：...
代码路径：A 调用 B，B 在条件 C 下执行 D
错误机制：...
证据：日志行 / JFR 计数 / 字节码条件（逐条列）
```

## 7. 修复设计 checklist

- 最小改动原则：先考虑「能不能不碰引擎，只改配置 / 路由」。
- 修复必须可回滚：配置开关（默认值经评估决定）或快速回退路径。
- 修复必须可观测：状态行 / 日志 / 计数器。
- 副作用：列受影响调用方，逐条验证。

## 8. 验证

1. 原 bug 场景：修复前失败、修复后成功，同一实体 / 同一配置；无法复现的 bug 以日志证据 + 代码逻辑走查为验证依据。
2. 回归：跑冒烟测试；相关旧 bug 场景手动再过一遍。
3. 边界：区域边界、未加载区块、重启后状态。
4. 性能：改前后 spark 同口径对比（见 §10）。

## 9. 方案归档与结果记录（强制）

1. **方案归档（`docs/scheme/`）**：方案定稿（评审通过）后、实施前，保存到 `docs/scheme/`，文件名 `YYYY-MM-DD-<主题>.md`。必须包含：背景 / 问题、方案（含为何不选替代方案）、改动文件清单、预期收益与风险、验证计划。
2. **冒烟测试前保存记忆**：跑冒烟测试之前，把当前方案、改动内容、预期结果、验证口径保存为记忆——会话中断后凭记忆即可恢复现场继续，不依赖对话历史。
3. **结果归档（`docs/summary/`）**：跑完冒烟测试后，输出改前 vs 改后总对比（同口径：TPS / MSPT / 违规计数 / 冒烟检查单逐项），并保存到 `docs/summary/`，文件名 `YYYY-MM-DD-<主题>.md`。必须包含六要素：**方案、性能对比（带数据）、优点、缺点、未完成、已完成**。

## 10. 优化 / 方案文档（A/B 文档）规范

- 前置必写：文档性质 + 对应审计文档出处、审查基线（分支 + HEAD commit）、验证环境（prts-test、NeoForge 1.21.1 + 构建版本、RCON 控制）。
- 问题分析须贴源码证据（反编译 / 字节码 / javap 运行时核对）；无收益即取消立项并记录理由。
- 方案 A/B 必写「为何不选替代方案」；改动文件逐文件清单。
- 模组兼容红线逐条核对表；遗留 / 未做事项必记录（含不做理由）。
- 运行时复验：`-Dmixin.debug.export` 导出确认 mixin 生效；门控探针验证后必删。
- 完成后把结论输出为新文档，不修改既有文档。

## 11. 性能对照口径（同口径才可比）

- 同负载、同插件状态；交叉 A/B；全预热；取中位；≥6 次会话复测。
- 对照腿用同配置重启，消除构建差异。
- spark 归因规则：`self = inclusive − Σ(child inclusive)`；先剔 idle（park / yield / wait）再归因。
- 回归断言：事件计数逐位一致、返回顺序一致、0 异常、0 线程违规（`BEPolicy unsafe=0`、`Journal dropped*=0`）。
- 冒烟测试每项必须过，FAIL 任意一项不进入下一步；产物 `smoke-report.log`。

## 12. 测试分级

- A 正确性 / 安全：单人可裁定。
- B 机制性能：合成负载 2~3 次取中位。
- C 容量 / 体感：真实多人生产。
