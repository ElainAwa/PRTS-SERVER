1.2 根因链（多次深挖后的最终定论）

⚠️ 压力不在 PRTS 核心，在模组事件洪流
  • EventBus.post 子树 inclusive 57%→75.5% —— 最大单一热点：破方块类模组触发 Forge 事件，多态派发 + HashMap 查找 + 锁竞争被放大

  • DestructionTaskState.copyTags（RTSbuilding）~7.2% —— 破坏任务在事件总线做 NBT 拷贝
  • ServerChunkCache.tickChunks 16.3% —— 结构性基线（sim=10 × 2.2 万区块），非 mod 造成
  • native 18.77% —— 纯下游症状（派发+锁+写盘），源头减量后回落
  • PRTS 核心引擎税仅 2.56% —— 已证伪「核心卡顿」嫌疑

1.3 「最卡顿的是世界计算」—— 定论链

  1. 网络（8 Netty 线程）与区块 IO（异步保存）早已异步化，不是瓶颈；
  2. 剩下没被异步化的就是主线程世界 tick 计算本身（区块/实体/方块/TE tick + 模组事件）；
  3. PRTS 单 tick 线程只占 1 个逻辑核，生产 48T 其余核全空闲。
💡 多线程方案的全部价值 = 把「世界计算」从 1 核摊开
P1（异步寻路）/ P2（维度并行）/ P3（区域并行）—— 全部以「并行化世界计算」为对象。这是 2026-08-06 写总方案（folia-copy-based-parallelism-v01.md）时确立的立论基础。

2 总方案：副本化区域并行

2.1 三条「不可能」结论

路线结论为什么死
Folia 区域化对 Forge/NeoForge 模组兼容 ≈ 0模组全假设单主线程安全访问世界；Folia 要求模组用 RegionizedData 重写 = 放弃现有生态
透明 shim「骗模组以为单线程」不可行共享可变状态 + 直接对象引用 + 单线程免费一致性消失 + 跨区依赖；field 级访问无法方法级拦截
副本化区域并行（第三条路）可行（本项目采用）不给模组同一个 Level，而是给每个区域一个独立的权威副本 —— 模组持有的引用本身就是区域本地的，区内语义 100% 一致

2.2 核心思想

🧠 不是「假装单线程」，而是「世界本身就是多副本的」
  • 模组代码在区域线程上运行，拿到的 ServerLevel 引用是区域权威副本（RegionLevel）
  • 区域内的一切读写发生在本地副本 —— 单线程、直接引用、免费一致性，与主线程语义完全一致
  • 「不可能」收缩为一个协议性问题：跨区更新怎么同步（更新集 + authority + 请求-应答）

2.3 工程落地的关键让步（实验期 RegionLevel 不是完整副本）

完整数据副本需要克隆 ChunkMap/实体管理器/存档层（人月级），因此实验期采用「共享数据 + 严格 tick 分片 + 跨区路由」：

  • RegionLevel 是主 ServerLevel 上的区域视图（非 ServerLevel 子类）：regionId + chunkRange + 本区 tick 任务列表 + 跨区路由门
  • 区块数据仍在主 ChunkMap（共享）；安全前提：区域内 tick 只读写本区域区块，跨区访问一律走路由 —— 共享 ChunkMap 的并发面 = 仅区块加载/卸载生命周期（主线程管理）
  • 总方案 §2 的「完整权威副本」是最终形态（Phase 4 工程），协议对了数据隔离只是实现替换

4 P1 异步寻路

原理为什么寻路要异步

PathFinder A* 是 CPU 密集计算，且实体寻路请求集中在 AI 调度瞬间（成百上千 mob 同时重算）。在主线程/区域 worker 内同步执行会直接阻塞世界 tick。P1 把 A* 从 tick 线程剥离：计算与状态分离 —— 提交时捕获不可变快照，任务池只读快照计算，结果下一 tick 应用。

实现核心组件

组件职责关键点
AsyncPathfindingManager任务池 + 结果队列 + drainMAX_PENDING_TASKS=1024 容量门限（满则同步回退）；PRTS-AsyncPathfinding-* daemon 池
PathFinderMixin_Async@Inject findPath HEAD 提交提交条件 serverThread ∨ dimensionWorker ∨ regionWorker（isParallelTickThread()）；提交成功返回 null（实体沿旧路径继续）
ImmutablePathNavigationRegion不可变快照底层改为可复用的 ImmutableBlockView（只读 BlockGetter + BlockState 引用数组），不引用活区块 → 任务池计算安全
PathNavigationMixinarclight$asyncPending + applyAsyncResultvolatile pending 标记；应用时恢复 speedModifier、保留 pathKeep/trimPath 影子字段，结果只由持有实体的线程应用（08-14 生物静止三连修复）
// 提交 → 任务池 → 结果 → 应用（P1×P3 按 region 分桶后）
submit(..., regionId):
  regionId < 0 → RESULTS 主队列（serverThread / 维度 worker）
  regionId >= 0 → RESULTS_REGION[regionId]（区域 worker，本区 drain）

效果

  • 寻路计算从主线程剥离，A* 不再阻塞世界 tick
  • 结果应用 1 tick 延迟窗口（提交 tick → 下 tick 应用），与更新集协议语义一致
  • 区域 worker 内寻路 offload 后，区域会话墙钟时间下降（切片 4 目标）
  • 池饱和回退策略：MAX_PENDING_TASKS 满时跳过本次提交并保留实体当前 path（旧实现会清空 path 导致 mob 原地不动），绝不在 region worker 上同步搜索拖垮会话

5 P2 维度并行

原理维度间天然低耦合

主世界/下界/末地的 tick 内容互不依赖（红石不跨维度、实体不跨维度），维度间交互仅传送/Portal/玩家切换 —— 是「区域 = 维度」特例下 tick 边界同步协议的最佳验证场。P2 跑通 = 方案从「理论成立」变「工程可行」。

实现调度与线程安全

组件职责关键点
DimensionTickManager.parallelTick维度 worker 调度pre 事件 → worker×M level.tick() → CountDownLatch 屏障 → post 事件 → pendingTransfer/pendingEvents drain
MinecraftServerMixin_DimParallel@Redirect tickServer 主循环世界数组包装为 DimensionTickUnit[] 传入
ServerChunkCacheMixin_DimParallelworker 内 getChunk 线程安全lastChunk 环形缓存 + visibleChunkMap volatile 快照 + getFullChunkFuture().getNow + 整体 try-catch（B9 最终版）
EntityMixin_DimTransfer跨维度传送延迟pendingTransfer 队列，屏障后主线程执行（避免 worker 等主线程死锁）
SimplePluginManagerMixin_DimParallelBukkit 事件放行isPrimaryThread ordinal=1 放行维度/区域 worker 内事件派发

效果P2 实战沉淀三条铁律（P3 必须遵守）

🔒 三条铁律
  1. supplyAsync future 在主线程 barrier 期间永不完成 —— 任何「非主线程等主线程执行器」模式都是死锁（B5/B8 watchdog 教训）
  2. fastutil 容器非线程安全 —— 跨线程读必须「volatile 整体替换引用」或「纯数组无锁读」，禁止裸并发读可变 map（B7 watchdog 教训）
  3. BootstrapMethodError 类链接失败 —— AsyncCatcher 对 void 方法 Supplier 包装的根因已根治（injectCheck 跳过 void）；新并行路径避免引入新的 invokedynamic 依赖

6 P3 区域并行：原理（协议层）

P2 证明「区域 = 维度」特例下协议成立；P3 把粒度细化到主世界内区域，验证协议的高耦合强度承载能力（同维度内实体/方块/红石/追踪持续交互）。

原理6.1 静态条带划分

STRIPE_WIDTH = 8（chunk 周期）
N=2: regionId = floorMod(chunkX,8) >= 4 ? 1 : 0   // 前 4 chunk → region0，后 4 → region1
边界在 x=0 与 x=-1 之间；边界带 = 紧邻边界两侧各 1 chunk 列（其更新走更新集广播）

为什么静态不动态：动态 regionizer（Folia 式负载合并/分裂）是优化不是正确性前提；静态条带先验证协议正确性，且「重配置 = 换划分函数」为 v11/v12 铺路。

原理6.2 三会话拆分（v04）

会话内容同步
会话 1方块 scheduled tick区域 worker 并行，latch 同步区域内原版顺序（每 tick 三会话依次执行）
会话 2实体 tick
会话 3方块实体（TE）tick

归属纪律：实体/方块/TE 按「所在 chunk」归属区域 —— 同一 chunk 的所有 tick 责任落单一区域，杜绝「一 chunk 两线程」。

原理6.3 更新集协议（v03）→ 跨区写日志 journal（v1.0.36 加固）

阶段 1（区域 worker tick 内）: 收集跨区更新
  ─ 方块跨区写 → 记录 (pos, blockState, 原版邻居更新语义) 到本区更新集 U
  ─ 实体越界 → 标记 transferring，冻结本地权威写，实体快照入转移队列
阶段 2（barrier 后，主线程）: 分发与应用
  ─ 按目标区域拆分更新集 → 目标区域下一 tick 开始前应用
  ─ 实体转移 → 目标区域先接管后 tick（源区先摘除）—— 任何时刻 tick 责任唯一

v1.0.36 加固（WorldWriteJournal）：跨区写由每区 journal 队列承载 —— journal-max-per-region（默认 4096，最旧丢弃）、未加载/过期目标丢弃、源区域与 tick 元数据、droppedOverflow/droppedUnloaded/failed 计数与 /servercore status 观测。journal-read-back 预留 read-your-writes overlay（默认关）。更新集语义不变：1 tick 最终一致窗口。

原理6.4 authority 转移与跨区读路由

  • authority：实体跨区移动 → 源区冻结 → 屏障交快照 → 目标区接管。玩家实体跨区网络包由主线程 playerList 衔接（P2 已验证无感知）
  • 跨区读（请求-应答）：请求入队 → 不阻塞返回占位值（方块读空气/TE 读 null）→ barrier 后主线程应答 → 下一 tick 应用。延迟 1 tick 与更新集一致，调用方读到占位后自然重试；应答队列上限 4096，满则丢弃计 cross-read-dropped
📏 跨区读是「测量仪器」
cross.read counter 是 P3 首要指标 —— 每 tick 跨区读频繁 = 划分切割在高耦合线上，应调整条带边界。

原理6.5 激活范围与线程归属（v1.0.36）

  • 激活范围修复：原扫描挂在 EntityTickList.forEach 的 invoke 注入点上，区域并行接管 forEach 后扫描被整体跳过 → 离玩家较远的 mob 恢复 tick 失败。现前移到 ServerLevel.tick HEAD，与派发方式解耦。
  • ThreadPolicy 线程归属：worker 上的世界访问违例按 violation-log-per-minute 限流记账；main-thread-routing=auto 时违例实体类从下一 tick 起自动路由主线程（route-threshold / route-window-ticks），manual 只认 main-thread-entity-force 种子列表。

7 P3 区域并行：实现（代码层）

实现7.1 调度架构（方案 B：主世界维度单元内拆分实体 tick）

P3 开启时主世界仍是维度单元（level.tick 整体在维度 worker 跑），但 ServerLevel.tick 内的 entityTickList.forEach 被 @Redirect 到 RegionTickManager.dispatchAndTick：

维度 worker（主世界 level.tick）:
  forEach 调用点 → dispatchAndTick(level, entityTickList)
    1. 遍历实体列表，按 chunk 归属（RegionLevel.regionId）投递到区域队列
    2. 区域 worker×N（PRTS-RegionTick-*）并行 tick 各自队列（复刻 vanilla forEach 语义）
    3. latch 等待全部区域完成 → 返回 level.tick 继续
实体越界 → 下一 tick 重分派自动归属（authority 简化为全量重分派）

为什么不做完整区域单元（方案 A）：方块/TE tick 按区域过滤工程量大且易漏/双跑；实体 tick 是主要负载，先并行化收益最大、风险最小。方案 A 后置（v04 三会话落地）。

实现7.3 实体管理两级锁（v05）

实证洞察（javap 读写路径全景）：EntityLookup.byId/byUuid 只在 add/remove 写；EntitySection 完全属于单个 chunk → 单区域（区内同 worker 串行 tick，天然互斥）；并发写同 section 仅跨区移动（罕见）与主线程 spawn/remove（低频）。

级保护对象锁性能要点
L1EntityLookup(byId/byUuid)、EntitySectionStorage(sections/sectionIds)、EntityTickListstatic ReentrantReadWriteLock（读多写少）高频区内移动零 L1 锁（onMove 只动 section 不动 lookup）
L2EntitySection 元素集合per-instance @Unique ReentrantReadWriteLock（v11 改注入字段）区内无竞争（同 worker 串行），仅跨线程时竞争
  • 锁序纪律：L1 → L2 固定顺序；onMove 先释放旧 section 锁再取新锁（不存在 L2-L2 嵌套）→ 无死锁
  • 无锁快速路径（容忍微秒级 stale，1 tick 自愈）：getOrCreateSection 已存在分支、getEntity、getAllEntities
  • EntityLockManager.java：L1 全局锁单调用点、从不嵌套

实现7.4 mob AI 修复（v08 关键发现）

🐛 NeoForge 1.21.1 把 AI 调度从 Entity.tick 拆出
  • 现象：区域 worker 下 zombie/villager 完全呆滞（60s 位置不变、0 寻路），主线程对照正常
  • 根因（javap 实证）：Entity.tick 精简为仅 baseTick()；AI 调度（goalSelector/Brain）移入 serverAiStep()（protected），且只由主线程 tick consumer 调用。区域 worker 用 tickNonPassenger（=baseTick）→ AI 静默丢失
  • 修复：tickEntity 补调 serverAiStep()（@Invoker，必须 abstract class 模式 —— 接口 mixin 不支持 @Invoker，v08k 曾 ClassCastException）。先试 aiStep()（public）无效（goalSelector 不在 aiStep）
  • 实测：cross.read 56/tick vs 修复前 18.8/tick（3 倍提升）→ AI 调度恢复生效

9.2 诊断方法论（可复用）

🔬 三招定位并行 tick 崩溃
  1. 线程栈交叉比对：crash-report 里主线程栈（latch.await 位置）+ 区域 worker 栈（join/checkOp/事件链）同时看 —— 一锤定音「谁等谁」
  2. 共享可变状态分类：LegacyRandomSource 与 getChunk 同族 —— 把共享单线程实现换成线程安全实现（createThreadSafe 是 Level 已备好的字段）
  3. 「逻辑 bug vs 并发竞态」区分：stopTracking 负索引是逻辑 bug（加锁不解决）→ 跳过合并防御；AreaMap 越界是竞态 → 内部锁

10 v11 参数化：原理 / 实现 / 效果

原理为什么先做静态 N 再做动态

动态合并/分裂涉及「区域边界移动时实体/TE/方块 tick 归属迁移 + 更新集路由变化」，与 authority 转移耦合，是 P3 剩余风险最高的工程；而静态 N 参数化的所有协议（更新集/authority/跨区读）按 regionId 寻址，天然与 N 无关。先落地 N=4/8 拿收益，再谈在线动态。物理核视角目标是 4-8 核收益区（总方案 §3.3）。

实现划分函数泛化

public static int regionId(int chunkX) {
    int group = Math.floorMod(chunkX, STRIPE_WIDTH);   // 0..7
    int perRegion = STRIPE_WIDTH / regionCount();      // N=2→4chunk/区, N=4→2chunk/区, N=8→1chunk/区
    return Math.min(regionCount() - 1, group / perRegion);  // 除法取整 + min 双保险防越界
}
N每区宽合法性
24 chunk与旧行为完全等价（零回归）
42 chunk默认值
81 chunk边界带占比最高
160.5 chunk不合法（需 STRIPE_WIDTH 扩到 16，后置）

14 已知风险与未来演进

14.1 四大深层问题（总方案评审确认）

风险分析对策
跨区引用身份语义跨区返回快照非权威对象，写不自动同步（对象身份问题，非数据新鲜度）—— 决定模组兼容上限Phase 4 已部分落地：ImmutableBlockView 只读快照用于异步寻路；写拦截 + 值快照 API 仍后置
远程状态内存膨胀完整区块克隆最坏 4x 内存（4 区域），GC 杀 TPS缓存≠克隆：Phase 3 无缓存，Phase 4 轻量快照（弱引用 + 窗口配额）
确定性异步边界同步下更新集应用顺序非确定文档化语义差异 + 确定性模式开关（tick barrier 全序化，默认关）
红石跨区级联时序跨区红石 1 tick 窗口导致传播翻倍（3gt→6gt+）边界合并区 + 实测 <1% 达标 → 红石子求解（NP 难）免做

14.2 N 增大的固有代价

每区宽变小 → 边界带数量翻倍 → 跨区写/读/红石传播概率上升。区域数不是越高越好 —— 依赖 cross.read 指标 + 动态调节自愈（边界开销爆炸时自动退回 4）。

14.3 未来演进方向

  • 多线程架构分级：PRTS 稳在 L1（单主线程 + 异步区块IO/Netty/聊天定时器离主）；可行演进 L2 并行区块生成 + L3 异步寻路/实体追踪；不能上 L4 Folia / L5 Minstom（模组兼容红线：假设单主线程拥有世界状态）
  • N=16：STRIPE_WIDTH 动态扩到 16（一处常量变函数），边界带占比过高，等 N=8 实测数据再定
  • 不等宽条带：条带等分对「负载集中某条带」不敏感；真正动态 = 区域边界按负载偏移（贪心重平衡），MVP 后置
  • 完整数据副本：把「共享读取」换成「本地副本读取」是 Phase 4 剩余工程；寻路快照已用 ImmutableBlockView 验证只读路径，完整 RegionLevel 副本仍后置
